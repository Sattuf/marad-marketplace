# خطة التنفيذ الرئيسية — من «يعمل» إلى «قابل للنشر والنمو»

> كُتبت: 2026-11-27 · المالك: Sattuf · المنفّذ: وكيل Claude بدور Staff Engineer + مهندس أمن + مسوّق.
> هذا الملف هو «البرومبت» الثابت لكل جلسة عمل. لا يُعدَّل إلا بقرار مسجّل في `docs/DECISIONS.md`.

## 1. المهمة

نقل «معرض الأشياء» من مشروع يعمل محلياً (11 خدمة، ~300 اختبار، CI أخضر) إلى **تطبيق منشور فعلاً**:
بيئة تجريبية (staging) حقيقية على الإنترنت بقاعدة بيانات حقيقية، صفحات قانونية منشورة، متطلبات
Google Play وApp Store مستوفاة، ثم ميزة «الأرخص من المنصات الأخرى» بالمواصفات في
[EXTERNAL_OFFERS_PLAN.md](EXTERNAL_OFFERS_PLAN.md).

**تعريف «انتهى»:** رابط staging يعمل من أي هاتف؛ تسجيل → نشر إعلان بصورة → بحث → محادثة → صفقة
→ تقييم → حذف الحساب، كلها على قاعدة Supabase حقيقية؛ CI أخضر؛ لا ثغرة حرجة أو عالية مفتوحة؛
ملف APK موقّع قابل للتثبيت؛ صفحات الخصوصية والشروط وحذف الحساب منشورة بروابط ثابتة.

## 3. طريقة تنفيذ كل خطوة (الحلقة الثابتة)

1. **اقرأ** `PROGRESS_LOG.md` (آخر جلسة) ثم `NEXT_STEPS.md` (المهمة التالية وتفاصيلها).
2. **فرع:** `git checkout -b launch/<ID>-<slug>` من آخر فرع مدموج.
3. **اختبار أولاً** حيث يمكن: اختبار يفشل يثبت المشكلة أو يصف السلوك المطلوب.
4. **نفّذ** بأصغر diff يحقق معيار القبول. لا إعادة كتابة بلا سبب مسجّل.
5. **تحقق محلياً:** typecheck + lint + اختبارات الخدمات المتأثرة + `next build` إن لُمس الويب.
6. **ادفع** وانتظر CI على GitHub Actions (المكدس الكامل + e2e + CodeQL + Trivy + gitleaks).
7. **مراجعة أمنية** للـ diff بالقائمة في §4، تُكتب في سجل المهمة (سطر لكل بند منطبق).
8. **سطر تسويقي** إن كان للمهمة أثر مرئي: ما الذي تغيّر للمستخدم، وكيف يُقاس.
9. **سجّل** في `PROGRESS_LOG.md` (ما تم + الدليل: أرقام اختبارات، رابط run)، وحدّث `NEXT_STEPS.md`.
10. **فشل بعد 3 محاولات؟** علّم ⛔، اكتب ما جُرّب ولماذا فشل في `IMPROVEMENT_BACKLOG.md`، وانتقل للتالي.

## 4. قائمة المراجعة الأمنية لكل diff

- [ ] **المصادقة والتفويض:** كل مسار جديد له حارس؛ المالك يُتحقق منه في الخادم لا من العميل (IDOR).
- [ ] **المدخلات:** DTO بـ class-validator / Pydantic، حدود طول، رفض الحقول الزائدة.
- [ ] **الأسرار:** لا شيء في الكود أو السجلات أو رسائل الخطأ؛ متغير بيئة إلزامي بلا قيمة افتراضية.
- [ ] **البيانات الشخصية:** أقل قدر ممكن؛ لا تُسجَّل؛ تُحذف مع الحساب.
- [ ] **المعدل والإساءة:** حد معدل لكل مسار عام ومكلف (SMS، رفع، بحث، `/out`).
- [ ] **الحقن:** استعلامات معاملات فقط؛ لا HTML من مصدر خارجي؛ رؤوس CSP.
- [ ] **الملفات:** حد حجم، تحقق من النوع بالمحتوى لا بالامتداد، أسماء عشوائية بـ `randomUUID`، إزالة EXIF.
- [ ] **الاعتماديات:** `npm audit --omit=dev` و`pip-audit` بلا حرجة/عالية.
- [ ] **Supabase تحديداً:** لا جدول مكشوف عبر PostgREST للمفتاح `anon` (§6.2).
- [ ] **الجوال:** لا أسرار في APK؛ HTTPS فقط؛ لا تسجيل للرموز.

## 6. البيئات

### 6.1 الثلاث
| البيئة | أين | قاعدة البيانات | الغرض |
|---|---|---|---|
| محلي | `make up` على جهاز المطوّر | Postgres في Docker | التطوير |
| CI | GitHub Actions | Postgres في Docker، ثم job منفصل على Supabase | كل push على `launch/**` |
| staging | Vercel (ويب) + VPS (خدمات) | **Supabase** | تجربة حقيقية من الهاتف، رابط يُشارك |

### 6.2 Supabase — قواعد إلزامية
- الاتصال من الخدمات عبر **Session pooler** (IPv4) بـ `sslmode=require`، ومن الترحيلات عبر الاتصال المباشر.
- **خطر مهم:** Supabase يكشف مخطط `public` عبر REST API لأي شخص يملك مفتاح `anon` (وهو علني بطبيعته).
  جداولنا في `public` → يجب: (أ) إزالة `public` من «Exposed schemas» في إعدادات API، **و**(ب) تفعيل RLS
  على كل الجداول بلا سياسات (رفض افتراضي)، **و**(ج) `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated`.
  يُضاف اختبار في CI يحاول القراءة بمفتاح anon ويتوقع الرفض.
- لا تُستخدم مفاتيح `service_role` في أي خدمة؛ الخدمات تتصل بمستخدم Postgres مخصص.
- الامتدادات المطلوبة: `pg_trgm` (متاح في Supabase). التقسيم (partitions) مدعوم.
